01

Are all lessons generated?

Yes. 94 lessons across all twelve modules, zero failed.

28 theory lessons, 19 labs and 47 preparation sessions — one before every content lesson, alternating prep → lesson → prep → lesson, in all twelve modules. 654,000 characters. Every single preparation session has all four parts: priming, reading, review and questions with answers, and all 47 mark their reading as required or optional with a page count.

The rule that stopped it was called one module ahead: content follows the pace so that a track abandoned after module two never pays for module nine. It remains the default. What was added is an explicit per-track opt-in — when the owner has already decided, a cost guard should not overrule the one paying the cost.

The Boehm gap is fixed. The measurement showed zero reading references to his paper in all twelve modules — even though module 2's whole thesis is that paper. The cause was concrete: the instruction asked for chapters, and a twelve-page paper has none, so it fell out. The rule now says that a source without chapters is assigned in full. Module 2's second preparation session now says "Boehm, Threads Cannot Be Implemented as a Library (PLDI 2005) — read all of it, about 12 pages. REQUIRED."

And only there. A paper belongs in one place; sprinkling it into modules 4, 7 and 9 would have been padding, not coverage.

Drepper first looked missing in the same way but was not — he was cited under the book's title and never under his surname, so the first measurement reported zero for him too. That the two cases looked identical and were completely different things is the whole reason to measure instead of guess.

How do you create a test for a new thing?

Put it in any tests/*.c. Registration happens through a constructor — no list to update, no main to touch.

/* tests/test_spinlock.c — new file, picked up automatically by the Makefile */
#include "para_test.h"
#include <paracore.h>

/* PARA_TEST_RACE tags the test as race-sensitive.
   `make stress` runs ONLY these, 200 rounds, under TSan. */
PARA_TEST_RACE(mcs_lock_releases_in_fifo_order) {
    para_lock *l = NULL;
    PARA_ASSERT_OK(para_lock_init(&l, PARA_LOCK_MCS, 8));

    /* ... start threads, measure the order ... */

    PARA_ASSERT_EQ(observed_order, expected);
    para_lock_destroy(l);
}
  • PARA_ASSERT_OK(expr) — requires PARA_OK, prints para_strerror otherwise.
  • PARA_ASSERT_STATUS(expr, PARA_ERR_BUSY) — for the expected errors.
  • PARA_ASSERT_NOT_BUILT_YET(expr) — the one in test_notimpl.c today. When you build the module it fails, and that is the signal to come back and write the real test.
  • A deadlock becomes TIMEOUT with the test's name after 10 s, not a hung suite. A crash becomes SIGNAL with the signal name. Both thanks to one process per test.
06

What does the dev loop look like?

  1. 01
    make progress Which file owns the module you are on? The list is computed from the source, not from a README that drifted.
  2. 02
    Open the stub, read the header above it The comment is the spec: which variants, which order, and why each one exists.
  3. 03
    Remove return PARA_ERR_NOTIMPL, write the simplest variant Coarse before fine. The reference first — everything else should beat it, and without it there is nothing to beat.
  4. 04
    make test Seconds. test_notimpl.c now fails for your module — remove the row, write a real test.
  5. 05
    make tsan and make stress A concurrency test that ran once has not proven anything. 200 rounds under TSan has.
  6. 06
    make helgrind for every new lock Finds lock-order inversions that never happened at run time. What TSan does not always see.
  7. 07
    make asan when you start freeing memory From module 9 onwards this step is the whole point, not a formality.
  8. 08
    make bench + measure, then the next variant Every step in a module exists because the previous one measured badly. Without the number the order is arbitrary.
  9. 09
    make check before committing fmt + test + tsan + asan + canary. The final heading says ALL GREEN only if every lane actually ran.
07

The three outcomes

The repo's only real rule about tools, and it has paid for itself four times this week. A tool that could not run has not answered "no" — it has not checked anything at all.

caught / ok            the tool ran and gave an answer
SKIPPED / UNAVAILABLE  the tool could not run — the reason is printed
MISSED / FAILED        the tool ran and found nothing → the gate fails

Four times, all found by running the same commit on another machine: valgrind was missing and the gate failed as if the code were broken · helgrind crashed internally and looked almost like an acquittal · TSan does not start at the Pi's 47-bit VMA · clang-format was missing and fmt-check answered "ERROR — run make fmt", i.e. blamed the code. The last one was the worst.
